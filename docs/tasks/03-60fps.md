# Task 03: true 60 fps races for Top Gear 2

Read `AGENTS.md`, `docs/BRINGUP.md` and `docs/RAM_MAP.md` first.

## Setup in this worktree

You are in a fresh worktree:
- run `git submodule update --init --recursive`;
- build with `JOBS=8 tools/build-linux.sh ~/roms/genesis/tg2.bin build`.

Other agents run TG2Recomp instances in parallel on this machine:
- use **TCP port 4410** and only that one;
- kill only processes you started (by PID). Never `pkill TG2Recomp`.

Another agent is doing widescreen in parallel. Stay out of the video

## Goal

The host already runs the machine at 60 Hz. The question is how often the
**game** produces a new picture during a race. The goal is a race whose
road, cars, scenery and HUD visibly update every 60 Hz frame. Game speed
and feel must not change: same lap times, physics, AI and music tempo.
Expose it as an option. With it **Off**, output stays byte-identical to
stock: frame 60 `2A0B972960C5E325`, frame 300 `1131D937D70234FD`, and the
race route in `game/baseline-route.json`.

## Phase A: measure (required before any change)

- Measure the real race update rate. Count frames whose race framebuffer
  (or VDP road/sprite/scroll state) differs from the previous frame, over
  a few seconds of the baseline route at steady speed. Report the
  distribution, e.g. "new picture every 2 V-ints", or variable 2–3 when
  the CPU is overloaded.
- Find the main race loop and its frame pacing:
  - the VBlank wait (`$FF01C6` handshake at `$002082`);
  - the race V-int counter `$FF238C`, whose parity schedules work.
  Which work runs each V-int and which on alternate ones? Is the game
  lagging (main loop takes more than one frame of 68k time) or deliberately
  capped?
- Find where per-tick deltas are applied: speed → track position, opponent
  advance, timers, lap clock, engine-pitch/sound timing.
- Write all of this up in `docs/FRAMERATE.md` with ROM addresses. Add new
  RAM fields to `docs/RAM_MAP.md`.

## Phase B: implement

Choose on the evidence and justify it in `docs/FRAMERATE.md`. Candidates:

1. **Lag-only.** The game is slow only because the 68k is overloaded. Let
   the main loop run without the emulated cycle budget during races
   (native code is fast), so it completes a frame every V-int. Then halve
   the per-tick deltas so speed stays authentic, or confirm the game
   already scales by elapsed V-ints (common: it reads the V-int counter
   delta).
2. **Fixed 30 Hz logic, 60 Hz presentation.** Run the game logic on its
   original cadence and generate intermediate frames by interpolating
   presentation state (road scroll/raster lists, sprite positions) between
   consecutive logic frames. Presentation-only, so game state stays
   authentic.
3. **Doubled logic rate with halved deltas.** Only if the tick deltas are
   cleanly identifiable.

Whatever you pick:
- Lap time over a fixed input route must match stock within one frame of
  game clock. Measure it: drive the same scripted inputs with the option
  off and on, and compare race clock/position/speed at matching
  wall-clock times.
- Music and sound tempo are unchanged.
- No new dispatch misses or floor entries.
- Menus are unaffected.

## Evidence required

- `docs/FRAMERATE.md` with the measurements (before and after), the chosen
  technique and its justification.
- A before/after count of distinct race pictures per second (target ~60).
- A lap-clock/speed comparison table, option Off vs On, on the same input
  route.
- Off-mode frame hashes equal to stock.
- A short PNG sequence (6 consecutive frames) under `build/fps/` showing
  every frame differs with the option on.

If true 60 fps isn't safely achievable, deliver Phase A in full plus the
best safe partial (e.g. presentation interpolation of the road only). Say
exactly what's missing and report it as partial.
